## 1. Wrong default clock (high)

`chart.py` returned `datetime.now()` when `reference_time` was omitted. That is the
container's UTC wall clock, and the rest of `build()` treats it as the **birth
location's** local clock. The explicit timezone-aware path was already correct; only
the omitted-argument default was wrong.

Measured on the live service:

| Birth timezone | Error in `as_of` |
|---|---|
| Asia/Kolkata | -5.5 h |
| America/Los_Angeles | +7.0 h |
| Pacific/Auckland | -13.0 h |

It reached the numbers: in `/v1/transits` the Moon was off by **2.83 degrees**, the Sun
by 0.23, Venus by 0.13 (Kolkata birth). Dasha boundaries are far less sensitive.

Why it mattered most: the LLM tool schema (`/v1/tool-definition`) has no
`reference_time` field, so the main consumer could never pass one and always got the
wrong clock. The `api.py` docstring claim "same input always yields the same JSON" was
also untrue for this reason.

Fix: take the current instant as aware UTC and convert it through the same path as an
explicit aware value. Seven tests added. Verified they fail on the unfixed code: 4 fail
on this IST host (Los Angeles, Auckland) and 6 fail with `TZ=UTC0`, which emulates the
container (adds Kolkata).

Why existing checks missed it: every suite passes explicit inputs against reference
data. Nothing exercised the default path. My own earlier check of the timezone-aware
`reference_time` fix covered the explicit case only.

## 2. Out-of-range dates returned HTTP 500 (medium)

`/v1/chart` with year 0001 raised `OverflowError`; years from about 3003 raised
`swisseph.Error` ("sepl_30.se1 not found"). Neither subclasses `ValueError`, and the
routes only catch `ValueError` and `FileNotFoundError`. Same class of bug as the polar
500 fixed earlier.

Fix: `build()` is now a thin wrapper that checks the year and converts both exception
types to `ValueError`. Supported range found by bisection: **21 to 3000**. The low end
exists because the dasha cycle starts up to 20 years before birth (years up to 19 fail
for some dates; 20 and above all passed). The high end is the Moshier documented limit;
3003-01-01 works but 3003-06-01 does not. 31 tests.

Related gap, found afterwards: `/v1/bala` bypasses `build()` and still returned 500 for
years 3500 and 5000 (`/v1/muhurta` already returned 422). Fixed separately with 9 tests,
including the `janma_*` branch, which computes the Moon outside the original `try`.

## 3. Silent precision downgrade (medium)

The shipped `ephe/` holds the `_18` files, covering about 1800-2400. Outside that range
swisseph quietly uses the Moshier ephemeris (about 1 arcsecond against 0.001). Confirmed
at 1500, 1799, 2400, 2401, 2600. The engine never read the returned flag, and
`engine.ephemeris` still said `swieph`. The README itself calls this "a trap".

Fix, additive only: `engine.ephemeris` now reports what was actually used for each
chart; `engine.ephemeris_note` appears only on fallback; `/health` gains
`ephemeris_coverage` (derived from the `sepl_NN.se1` filenames) and `supported_years`.
The mean node is excluded from the detection because it is an analytic series and always
reports Moshier.

## 4. Unbounded input (medium)

The API sits behind a Cloudflare Tunnel with no authentication. Measured in-process:

| Request | Cost |
|---|---|
| `/v1/places?limit=100000` | 8.8 MB response |
| 200 KB numerology name | 5.6 s, 11.5 MB response |
| `vargas` list of 5000 duplicates | accepted |
| Every flag on, `dasha_depth=4`, all vargas | 24.6 s, 1.1 MB (a documented feature; not capped) |

Added bounds: `places` `q` 1-100, `limit` 1-50, `country` max 100; numerology names max
100 each; `vargas` at most 16 items and duplicates rejected; `date`/`time` max 32,
`place` 200, `timezone`/`ayanamsa` 64. Ten tests; 7 fail without the fix, 3 are weak
(those inputs were already rejected for other reasons). The hand-written
`/v1/tool-definition` schemas do not show the new caps (open).

## 5. Concurrent heavy requests - NOT REPRODUCED

**This finding, as I first reported it, was wrong.** I measured three simultaneous
requests with `include_transits` and `dasha_depth=4` taking 148 s wall clock, about five
times worse than running them back to back, and called it strong evidence of a
throughput collapse. That measurement used `TestClient` threads on a machine that was
probably under load, and it does not hold up.

A diagnosis agent re-measured under a real uvicorn server with 1 to 8 concurrent heavy
requests: scaling was roughly linear at about 3.4 s per request (one anomalous point, two
concurrent at 13.0 s, was not explained), and a cheap request issued alongside took
0.05-0.25 s throughout. Profiling one heavy request: 46,875 lock acquisitions, the lock
held 2.70 s of 2.81 s wall, 0.008 s spent waiting. So the process-wide lock serialises
cleanly and almost all the time is genuine ephemeris computation done under it.

What is true: heavy requests are serialised, so the service has the throughput of one
core for them, and there is no cap on how many an unauthenticated client can queue.
That is a capacity limit, not a defect. Under artificial CPU oversubscription (48 busy
processes on 32 cores) three concurrent requests took 4.7x one, against an ideal 3x; the
agent did not determine whether the GIL or the OS scheduler is responsible.

Not merged: the agent also produced an optimisation (branch
`worktree-agent-acdcd874c7d4f4106`, commit `3fae030`) that holds the lock across chunks
of 64 scan steps instead of once per sample. Lock acquisitions per heavy request drop
from 46,875 to 699 and a single request goes from 2.81 s to 1.96 s, with byte-identical
JSON across 5 births and 3 endpoints (agent's own check, not re-run here). I left it out
because it optimises a problem that did not reproduce and changes the lock to an `RLock`
on a production path. It is available if the 30% is wanted.

## 6. Container hardening (medium, latent)

`.env` holds 12 Prokerala client secrets. `.dockerignore` did not exclude it and the
Dockerfile runs `COPY . .`. The CI-built image is clean (CI checks out a fresh tree);
verified on the running container: no `.env`, no `validation/.cache`, no `PROKERALA_*`
variables. The risk was a `docker build` run on the developer machine.

Done: `.dockerignore` now excludes `.env`, `.env.*`, `.claude`, `.github`, `tests`,
`validation`, `examples`, `deploy`, `*.md`; nothing in `astro_engine/` reads those paths.
GeoNames downloads use `curl -fsSL` over https (a 404 now fails the build instead of
saving an HTML page as the zip). A non-root user (`app`, uid 10001) was added after
checking that it is safe: the places index opens `mode=ro`, nothing else writes at
runtime, and on the homelab's real bind mount (644 files in a 755 directory) uid 10001
gets `swieph` and the identical Sun longitude to root (84.680073). The image built from a
clean `git archive` export (no `.env` in the context) and was then run as
`uid=10001(app)` with `ephe/` mounted read-only, as docker-compose does: `/health`,
`/v1/places` and `/v1/chart` all returned 200, the logs showed no errors, and every
planetary longitude matched an in-process main-thread build to 0.0000 arcsec,
identical to the live service. Caveat: Docker Desktop shows bind mounts as 0777, so
that run alone says nothing about permissions; the homelab check above covers that.
The test image was built before the range branch merged, so it lacks the new
`/health` fields; the final image will be rebuilt by CI.

## 7. Worker threads ignored the ephemeris path (medium, dev only)

Reported by the range agent and then measured rather than trusted. pyswisseph keeps the
ephemeris path per thread; `set_ephe_path` ran once at import, so threadpool workers
silently used Moshier. On this dev machine (no `SE_EPHE_PATH`) a worker thread differed
from the main thread by up to **0.59 arcsec**. The live service differs by exactly
**0.0000 arcsec**, because the Dockerfile sets `ENV SE_EPHE_PATH=/app/ephe`. So
production was never affected, and deploying the fix should not change any production
number; the README claim that `ephe/` is "found automatically" was untrue for a threaded
server outside Docker. Fix: a per-thread `_ensure_ephe_path()`, called under the lock.

## 8. Server path in error text (low)

The new range handling initially interpolated swisseph's message into the client-facing
422, and that message names the server's ephemeris directory. Removed from both the
chart wrapper and the `/v1/bala` handler; the original exception stays on `__cause__`.
